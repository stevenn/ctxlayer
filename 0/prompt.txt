## 7. Async jobs

- **Submit**: `mcp/async-submit.ts` `submitAsyncJob(env, {userId, sessionId}, conn, tool, args)` (L84-158). It reads and writes the D1 `async_jobs` table (dedup on a sha256 job key, 15-min retry-warm, 10-min stale running) and sends to `JOBS_QUEUE`. The session id is used only as a recorded value.

## 8. Server→client and long-lived stream use

- **Progress notifications**: `callWithHeartbeat` (`upstream-call-runner.ts` L201-221) sends `notifications/progress` every 25s via `extra.sendNotification` when the client supplied a `progressToken`. This is used on the inline proxied path (proxy-registry L721) and needs the per-request response stream.
- **`sendToolListChanged`**: proxy-registry L228 (from `reload_upstreams`). Delivering it requires the standalone GET SSE stream or the in-flight response.

## 2. How OAuth props reach tool handlers [I]
1. `@cloudflare/workers-oauth-provider` 1.2.4 sets `ctx.props` (decrypted grant props) and `ctx.auth = { token, audience, expiresAt, scope, userId, clientId }` before calling the API handler (`dist/oauth-provider.js:4530-4590`).
   - External tokens get `ctx.auth = { token, audience, scope: [] }` with no `clientId`.
   - 1.2.4 does not set the `Symbol.for("cloudflare.workers-oauth-provider.verified-context.v1")` symbol that `agents` checks first, so agents falls back to reading `ctx.auth`.
2. The agents handler (`handler-stateless-B5hU3dxK.js:33-52, 330-344`) builds SDK `AuthInfo` from `ctx.auth`: `{ token, clientId, scopes, expiresAt, resource: URL(audience), extra: { props } }`.
   - It only does this when `clientId` is non-empty, `audience` is an http(s) URL and `props` is a plain object.
   - The `AuthInfo` is passed to the SDK as `fetch(..., { authInfo })`.
   - Separately it runs the request, and the streamed response body, inside an `AsyncLocalStorage` context `{ props: ctx.props }`. If `authInfo` could not be built it falls back to that same `ctx.props`.
3. Inside a tool:
   - `getMcpAuthContext()?.props` returns your `completeAuthorization` props.
   - `ctx.http?.authInfo` returns `{ clientId, scopes, … }`.
   - The factory also receives `{ era, authInfo, requestInfo: Request }`.
   - It needs `nodejs_compat`, which `wrangler.toml:9` already has.

An `apiHandlers` entry with a plain fetch handler, following `docs/mcp-servers.md:183-201` and `docs/securing-mcp-servers.md:153-160`:
```ts
const mcpHandler = createMcpHandler(createServer /*, { allowedHostnames, allowedOriginHostnames } */);
apiHandlers: {
  '/mcp': { fetch(request: Request, env: Env, ctx: ExecutionContext) { return mcpHandler(request, env, ctx) } }
}
```
- The docs say: "OAuthProvider needs an object with a `fetch` method… Passing the handler function directly throws at startup."
- Your current wiring is `apiHandlers['/mcp'] = McpSessionDO.serve('/mcp', { binding: 'MCP_SESSION_DO' })` in `apps/worker/src/oauth/provider-config.ts:88-90`.
- Host and Origin checks: the handler only applies default allowlists to localhost and `*.workers.dev`. For a custom domain, set `allowedHostnames` and `allowedOriginHostnames` explicitly (`docs/mcp-servers.md:136-142`).

- **The `legacy` option** (`createMcpHandler-CLhGwQTn.d.mts:3829-3852`), `legacy?: 'stateless' | 'reject'`:
  - `'stateless'` is the default.
  - Each request is classified by whether it carries the per-request `_meta` envelope claim (`index.mjs:1048-1088, 1326-1351`).
  - A modern request gets a fresh factory instance with `era: 'modern'`. The SDK sets the negotiated version, installs the `server/discover` handler, and seeds client info and capabilities from the envelope. It validates `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`, plus `Mcp-Param-*` against `x-mcp-header`, and checks required client capabilities. An unsupported revision gets a 400 with `UnsupportedProtocolVersionError` (`index.mjs:1226-1315`).
  - A legacy request (no claim, including `initialize`, GET or DELETE, batches, posted responses, or a body that is not JSON) gets a fresh instance with `era: 'legacy'`, served over `WebStandardStreamableHTTPServerTransport({ sessionIdGenerator: undefined })`. Non-POST requests get 405 "Method not allowed." (`index.mjs:966-1033`).
  - `'reject'` answers legacy requests with the unsupported-version error, and answers legacy notifications with 202.
  - A function value throws: "route in user land with the exported isLegacyRequest(request) predicate in front of a strict (legacy: 'reject') handler."
- **What this means for each client type:**

  | Client | What happens |
  |---|---|
  | 2026-07-28 | `server/discover` returns `{ supportedVersions: ["2026-07-28"], capabilities, instructions? }` plus `ttlMs`/`cacheScope` (default 0 / private) and `_meta.serverInfo` (`mcp-DXXb3Vv3.mjs:1034-1040`; codec at `src-CX2iR2pK.mjs:3227`) |
  | 2025-11-25 / 2025-06-18 | `initialize` is answered by a fresh legacy instance, with the version negotiated from the legacy list (`mcp-DXXb3Vv3.mjs:1012-1027`). Each later POST is again stateless |

- **`Mcp-Session-Id`:**

  - The legacy stateless lane uses `sessionIdGenerator: undefined`, so it mints no id.
  - GET SSE: 405 on both lanes.
- **`list_changed`:** the modern path serves it through `subscriptions/listen` streams (`index.mjs:1264-1268`). Legacy clients get no list_changed in stateless mode, because there is no GET stream.

  - `agents` replaces the SDK's legacy fallback with its own adapter (`handler-stateless-B5hU3dxK.js:122-218`). ## 4. v1 → v2 differences for your API surface
Verified in the installed code [I]:
- **Imports:** `McpServer` from `@modelcontextprotocol/server` instead of `@modelcontextprotocol/sdk/server/mcp.js`. A v2 server cannot run inside `McpAgent` (`docs/mcp-servers.md:285`).
- **`registerTool`:** the config is `{ title, description, inputSchema, outputSchema, annotations, icons, _meta }` (`d.mts:3300-3318`).
  - The preferred form takes a Standard Schema such as `z.object({...})`.
  - The raw-shape `{ field: z.string() }` form is `@deprecated` but still accepted.
  - Callbacks are `(args, ctx: ServerContext)` and return `CallToolResult | InputRequiredResult`.
- **`registerPrompt`:** takes `argsSchema` instead.
- **`registerResource`:** takes `(name, uri | ResourceTemplate, metadata &amp; { cacheHint? }, cb)`.
- **Instructions:** `new McpServer(info, { instructions, capabilities, cacheHints, inputRequired, requestState })` (`d.mts:2762-2873`).
- **The `extra` → `ctx` change** (`d.mts:2073-2228`):

  | v1 | v2 |
  |---|---|
  | `extra.requestId` | `ctx.mcpReq.id` |
  | `extra.signal` | `ctx.mcpReq.signal` |
  | `extra._meta` | `ctx.mcpReq._meta` |
  | `extra.sendRequest` / `sendNotification` | `ctx.mcpReq.send` / `notify` |
  | (new) per-request envelope with client info and capabilities | `ctx.mcpReq.envelope` |
  | (new) MRTR state | `ctx.mcpReq.inputResponses`, `ctx.mcpReq.requestState&lt;T&gt;()` |
  | `extra.authInfo` | `ctx.http?.authInfo` |
  | request headers | `ctx.http?.req`, a web `Request` |
  | `extra.sessionId` | `ctx.sessionId` |

  - `ctx.mcpReq.elicitInput` and `requestSampling` throw on modern-era requests.
- **zod:** v2 depends on `zod ^4.2.0`. Your worker declares `^4.0.0`.
- **Tool-name validation:** `/^[A-Za-z0-9._-]{1,128}$/`. It only warns (`console.warn`), it does not reject (`src-CX2iR2pK.mjs:7122-7180`).
- **Tasks:** the 2025-11-25 task types are "@deprecated 2025-11-25 wire vocabulary with no SDK runtime" in 2.0.0.
- **Caching:** `ttlMs`/`cacheScope` are emitted on modern list, read and discover results via `cacheHints`; 2025-era responses never carry them (`d.mts:2637-2656, 2788-2805`).

From the SDK v2 guides [W] (`https://ts.sdk.modelcontextprotocol.io/v2/migration/upgrade-to-v2.html` and `support-2026-07-28.html`):
- There is a codemod: `npx @modelcontextprotocol/codemod@latest v1-to-v2 .`
- `McpError` is renamed `ProtocolError`, and `ErrorCode` is renamed `ProtocolErrorCode`.
- "Zod v3 is no longer supported." Zod ≥4.2.0 self-converts.
- `registerResource` requires a metadata argument; pass `{}` if you have none.
- Resource-not-found is now -32602.
- Tasks: the experimental tasks feature was removed (SEP-2663). The later Tasks extension keeps `tasks/get` and `tasks/cancel`; this may only be in versions after 2.0.0.

## 5. Spec 2026-07-28 [W]
Changelog (https://modelcontextprotocol.io/specification/2026-07-28/changelog):
- Removes `Mcp-Session-Id` and sessions (SEP-2567).
- Removes `initialize` and `notifications/initialized`. "Every request now carries its protocol version and client capabilities in `_meta`" (SEP-2575).
- `server/discover` is a MUST.
- The GET endpoint and `resources/subscribe` are replaced by `subscriptions/listen`.
- `ping` and `logging/setLevel` are removed.
- Tasks move to the `io.modelcontextprotocol/tasks` extension.
- MRTR uses `resultType: "input_required"`, and every result carries a `resultType` field.
- No `Last-Event-ID`.
- `ttlMs`/`cacheScope` are required on cacheable results.
- Roots, Sampling and Logging are deprecated.
- Dynamic Client Registration is deprecated in favour of Client ID Metadata Documents (CIMD).

Transport (`/basic/transports/streamable-http`):
- "Every POST request to the MCP endpoint **MUST** include an `MCP-Protocol-Version` header."
- `Mcp-Method` is required on all requests. `Mcp-Name` is required on `tools/call`, `resources/read` and `prompts/get`. "These headers are **REQUIRED** for compliance."
- Mismatches get 400 with -32020.
- Unsupported version: "**MUST** respond with `400 Bad Request` and an UnsupportedProtocolVersionError" (code -32022).
- Unknown method gets 404 with -32601.
- For legacy traffic, a modern-only server SHOULD answer "HTTP GET or DELETE… `405`", and for "`Mcp-Session-Id`… ignore it, and do not mint or echo session IDs."
- Fallback rule: on 400, if "the body is empty or is not a recognized modern JSON-RPC error, fall back to `initialize`". This is the fallback Claude's hosted clients use against your current 400.

Versioning (`/basic/versioning`):
- "There is no negotiation handshake."
- "A server… **MAY** implement both behaviors."
- "A dual-era server **MAY** serve both eras concurrently on the same endpoint."

`server/discover` (`/server/discover`): the result is `{ resultType, supportedVersions, capabilities, _meta["io.modelcontextprotocol/serverInfo"], instructions?, ttlMs, cacheScope }`. Instructions and capabilities travel here and in no other message. Per-request client info arrives in `_meta` under `io.modelcontextprotocol/clientInfo` (a SHOULD) and `clientCapabilities`.

Authorization (`/basic/authorization`):
- "Authorization servers and MCP clients **SHOULD** support… Client ID Metadata Documents."
- Dynamic Client Registration is a MAY and "is deprecated".
- "MCP servers **MUST** implement… RFC9728."
- Audience validation per RFC 8707 is a MUST.
- `iss` in the authorization response is a SHOULD (RFC 9207).
- Insufficient scope gets 403 with `error="insufficient_scope"`.
